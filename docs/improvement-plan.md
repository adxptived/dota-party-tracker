# План улучшений бота: стабильность, скорость, картинки

Дата: 2026-10-08. Три направления, в порядке важности:

1. **Стабильность** — бот отвечает быстро и честно, даже когда OpenDota (или Stratz, Steam CDN) лежит.
2. **Скорость** — команды отвечают из БД почти мгновенно, сеть догоняет фоном.
3. **Картинки** — главные отчёты одной карточкой-картинкой вместо простыни текста.

Каждый пункт: проблема (со ссылкой на код) → решение → файлы → тесты → критерий готовности.
Правила проекта действуют: сначала падающий тест, `pytest` + `ruff check .` перед «готово»,
коммиты `feat/fix/perf(scope): …` по-русски, новая настройка → `config.py` + `.env.example` + README.

---

## Что уже сделано (2026-10-08)

- `/match` — картинка матча (`match_image.py`, `hero_icons.py`), подпись, кнопки «📝 Текстом» / «🔗 Dotabuff»,
  фоллбек на текст при сбое рендера или отправки.
- `opendota.py`: сетевой сбой (`requests.ConnectionError`) больше не ретраится трижды, а ставит паузу
  60 с (`_OUTAGE_PAUSE`) — следующие запросы сразу падают `RateLimited`, команды берут кэш БД.
- `service.match_board`: обновление перед «последним матчем» ждём не дольше `MATCH_REFRESH_WAIT` = 6 с.

Было: при недоступном OpenDota «⏳ Считаю…» на `/match` висело ~35 с (3 попытки × 5 с connect-timeout +
паузы, несколько запросов подряд, и так на каждую команду).

## Часть A. Стабильность при падении OpenDota

### A1. Единый «предохранитель» провайдеров (circuit breaker)

**Проблема.** Логика «не ходить в сеть» размазана: `_blocked_until` в `opendota.py` (429 и теперь сеть),
у Stratz (`stratz.py`) — ничего: при падении Stratz каждая команда ждёт `timeout=(5, 25)` × 3 попытки.
У иконок — своя пауза промахов. Пауза фиксированная (60 с): при долгом падении бот раз в минуту
снова ловит таймауты в команде пользователя.

**Решение.** Модуль `mmrbot/health.py`:

```python
class ProviderHealth:
    """Состояние внешнего сервиса: up / down (пауза) / probing (одна пробная попытка)."""
    def allow(self) -> bool            # можно ли идти в сеть сейчас
    def success(self) -> None          # ответ получен → up, пауза сброшена
    def failure(self, exc) -> None     # сетевой сбой/5xx → down, пауза растёт: 60 → 120 → 240 … ≤ 15 мин
    def status(self) -> dict           # для /status и heartbeat: state, since, next_try, last_ok, fails
```

- После паузы пропускается **одна** пробная попытка (half-open); остальные запросы в это время сразу
  получают отказ. Успех → `up`, неудача → пауза удваивается.
- 429 остаётся отдельной логикой (`Retry-After`), но тоже через `ProviderHealth` (state `limited`).
- Экземпляры: `od.health`, `stratz.health`, `icons.health`. Потокобезопасно (lock).
- Смена состояния логируется **одной строкой**: `WARNING OpenDota недоступен (ConnectTimeout), пауза 60 с`,
  `INFO OpenDota снова доступен (лежал 14 мин)`.

**Файлы:** `health.py` (новый), `opendota.py` (заменить `_blocked_until`/`_pause_outage`), `stratz.py`,
`hero_icons.py`.
**Тесты:** переходы состояний на фейковых часах; рост паузы и потолок; одна пробная попытка при
параллельных вызовах; Stratz при сетевом сбое не ретраит и сразу отказывает следующим.
**Готово, когда:** при выключенной сети ни одна команда не ждёт сетевой таймаут дважды за паузу.

### A2. Не трогать сеть, когда провайдер лежит — и в командах, и в фоне

**Проблема.** `refresh_chat` → `refresh_player` по каждому игроку пытается сеть и ловит исключение
(`tracker.py:734`); фоновые задачи (`game_watch`, `opendota_backfill`, `stratz_backfill`, `finish_refresh`,
`heroes_refresh`, `steam_watch`, `scheduler.py:144–304`) делают то же самое каждые 2–4 минуты.

**Решение.**
- `refresh_chat`: если `od.health.allow()` = False — сразу вернуть игроков из БД, не создавая пул потоков.
- `refresh_player`: Stratz-дозаполнение пропускать при `stratz.health` down.
- Каждая фоновая задача в начале проверяет нужного провайдера и тихо пропускает тик (`log.debug`).
- `heroes_refresh` при недоступности переносит себя на +1 ч (сейчас пишет ERROR с трейсбеком раз в сутки и при старте).

**Тесты:** e2e «OpenDota лёг» (см. A10) + юнит: `refresh_chat` при down не вызывает клиента.

### A3. Честная пометка «данные устарели»

**Проблема.** `stale_note` (`formatting.py`) говорит про отдельных игроков, но не объясняет причину.

**Решение.** Единая строка под отчётом и в подписи картинки:
`⚠️ OpenDota недоступен с 00:34 — показаны данные на 00:30`. Берётся из `od.health.status()` и
`max(updated_ts)` игроков. Когда OpenDota жив — строки нет.

**Файлы:** `formatting.py` (`outage_note`), `service.py` (`_with_stale` → добавлять причину).
**Тесты:** нота есть при down и отсутствует при up; время в часовом поясе чата.

### A4. Бюджет ожидания для всех команд

**Проблема.** Ограничение 6 с сделано только для `/match`. `/stats`, `/player`, `/heroes`, `/graph`,
`/records`, `/compare`, `/together` ждут `gather_summaries` / `refresh_only` до конца
(`service.py:104–124`) — при медленном (не лежащем) OpenDota это 10–30 с.

**Решение.** Обобщить `_refresh_capped` (`service.py`) в `refresh_with_budget(…, budget=COMMAND_REFRESH_WAIT)`:
ждём обновление не дольше бюджета, иначе отвечаем из БД с пометкой A3, а обновление доходит фоном.
`gather_summaries` разделить на «обновить» (с бюджетом) и «собрать сводки» (всегда из БД).
Настройка `COMMAND_REFRESH_WAIT` (по умолчанию 4 с) → `config.py`, `.env.example`, README.

**Тесты:** медленный фейковый refresh (как `test_latest_match_does_not_wait_for_slow_refresh`) для
`render_board`, `render_player_board`, `render_graph_board`: ответ укладывается в бюджет, фоновая
задача доходит до конца и не отменяется.

### A5. Логи без простыней

**Проблема.** Ожидаемые сетевые сбои пишутся с полным трейсбеком (`exc_info=True` в
`tracker.py:738`, `:387`, `:155`, `scheduler.py` heroes_refresh) — при падении OpenDota лог за минуту
превращается в сотни строк, настоящие ошибки в нём теряются.

**Решение.** Хелпер `log_network_error(log, msg, exc)`: для `requests.RequestException`, `RateLimited`,
отказа предохранителя — одна строка `WARNING … : ConnectTimeout`; трейсбек — только для неожиданных
исключений. При down-состоянии повторные сообщения по игрокам гасить (раз в паузу).

**Тесты:** `caplog` — сетевой сбой даёт одну строку без `Traceback`, `KeyError` — с трейсбеком.

### A6. Прокси для OpenDota

**Проблема.** С некоторых сетей (в т.ч. локальная машина разработки) `api.opendota.com` недоступен
целиком, Steam CDN и Stratz при этом работают.

**Решение.** Настройка `OPENDOTA_PROXY` (например `socks5h://…` или `http://…`) → `requests` `proxies`
только для клиента OpenDota. Для SOCKS — зависимость `requests[socks]` (PySocks). Документировать, что
стандартный `HTTPS_PROXY` тоже работает, но затронет все запросы.
**Файлы:** `config.py`, `.env.example`, README, `opendota.py`, `__main__.py`, `requirements.txt`.
**Тесты:** клиент передаёт `proxies` в сессию; без настройки — не передаёт. Значение прокси не логируется
(в нём может быть пароль).

### A7. Запасной источник новых матчей — Stratz (флагом)

**Проблема.** Пока OpenDota лежит, бот не видит новых игр совсем: оповещения о конце матча, рейтинг,
MMR стоят.

**Решение.** Когда `od.health` down, а Stratz жив, `game_watch` берёт последние матчи игрока из Stratz:
`player(steamAccountId) { matches(request: {take: 10, lobbyTypeIds: [7]}) { id startDateTime durationSeconds
didRadiantWin lobbyType players(steamAccountId) { isRadiant heroId kills deaths assists … } } }`.
Матч сохраняется как обычный (`player_slot` = 0/128 по `isRadiant`), с пометкой `source = 'stratz'`
(новая колонка `matches.source`, миграция добавлением колонки). Когда OpenDota оживёт, сверка истории
дозаполняет поля (нужен upsert недостающих полей вместо «вставить, если нет»).

**Риски (проверить до включения):** комментарий в `stratz.py:134` — история игрока у Stratz отстаёт и
`lobbyType` там ненадёжен. Поэтому: (1) прогнать на реальных аккаунтах и сравнить с OpenDota за неделю;
(2) включать флагом `STRATZ_FALLBACK=1`, по умолчанию выкл; (3) матчи без уверенного `lobbyType == 7` не брать.
**Тесты:** нормализация ответа Stratz; fallback срабатывает только при down OpenDota; повторная сверка
OpenDota не создаёт дублей и дозаполняет поля; оповещение не уходит дважды.

### A8. Telegram: надёжная доставка фоновых сообщений

**Проблема.** Оповещения о матчах уже помечаются отправленными только после успеха
(`detect_new_games(mark=False)`), но сводки (`send_digest`, `weekly_summary`) и смена Steam-профиля при
`TelegramRetryAfter` / сетевом сбое теряются до следующего дня/недели.

**Решение.** Обёртка `send_with_retry` (уважает `retry_after`, 2–3 попытки, только для сетевых/лимитных
ошибок; `chat_gone` — без повторов). Дату сводки ставить после успешной отправки (как у оповещений).
**Тесты:** фейковый бот, кидающий `TelegramRetryAfter` один раз → сообщение ушло, дата выставлена;
постоянный сбой → дата не выставлена, задача не падает.

### A9. `/status` для админа и расширенный heartbeat

**Решение.** Команда `/status` (только админам, через `access`): состояние OpenDota/Stratz/Steam/CDN
(up/down с какого времени, следующая попытка), остаток суточного лимита OpenDota (`remaining_day`),
время последнего успешного обновления по игрокам, очереди бэкфилла (сколько матчей ждут деталей и Stratz),
размер кэшей. Тот же JSON — в файл `heartbeat` (Docker healthcheck продолжает смотреть на свежесть файла).
**Тесты:** рендер статуса на фейковых данных; не-админ получает отказ.

### A10. Набор тестов «OpenDota лёг»

`tests/test_outage.py`: фейковый OpenDota, который кидает `ConnectTimeout`. Проверяем, что:
- каждая команда и кнопка из `test_e2e_commands.py` отвечает данными из БД, без «Не удалось», с пометкой A3;
- суммарно клиент вызван не больше одного раза на паузу предохранителя;
- `game_watch`, бэкфиллы, сводки не падают и не пишут трейсбеков;
- после «оживления» (сброс фейковых часов) данные обновляются.

## Часть B. Скорость

Цели (p95, OpenDota жив): текстовая команда ≤ 1 с, картинка ≤ 1.5 с, кнопка периода ≤ 0.5 с.
При лежащем OpenDota — так же (ответ из БД).

### B0. Сначала замеры

**Решение.**
- Middleware в `bot.py`: одна строка на команду/кнопку —
  `perf cmd=/stats chat=… total=1.84s refresh=1.20s build=0.31s render=0.12s send=0.21s`
  (фазы отмечаются контекстным таймером в `service.py`).
- `scripts/bench.py`: на копии боевой БД гоняет `build_leaderboard(refresh=False)`, `build_records`,
  `build_mmr_series`, рендеры картинок — печатает время на каждую функцию.

Без этих цифр пункты B3/B9 не делать — оптимизировать то, что реально медленно.

### B1. Ответ из БД, если данные «достаточно свежие» (stale-while-revalidate)

**Проблема.** Фоновый `game_watch` и так обновляет игроков каждые 2–10 минут (`GAME_REFRESH_COOLDOWN`,
`GAME_IDLE_COOLDOWN`), но команда сама идёт в OpenDota, если игрок обновлялся > 3 мин назад
(`REFRESH_COOLDOWN = 180`, `tracker.py:35`). В итоге почти каждая команда после паузы ждёт сеть.

**Решение.** Две границы:
- `FRESH_ENOUGH` (≈ 10 мин): данные моложе — отвечаем сразу из БД, сеть не трогаем вообще;
- старше — отвечаем из БД **и** запускаем обновление фоном; ждём его только в пределах бюджета A4
  (для `/match` «последний» — да, для `/heroes` за месяц — нет: новые 1–2 игры не меняют картину).
Какие команды ждут обновления, а какие нет — таблица в `service.py` (явно, рядом с функциями).

**Тесты:** свежий игрок → клиент не вызывается; несвежий → ответ сразу, refresh вызван фоном.
**Ожидаемо:** `/stats` с 1–3 с до ~0.3 с.

### B2. Одно обновление игрока за раз (single-flight)

**Проблема.** `game_watch` вызывает `refresh_player` вне `_chat_lock` (`tracker.py:385`), команда — под
локом чата (`service.py:112`); один игрок в двух чатах обновляется дважды. Параллельные запросы к тому
же игроку тратят лимит OpenDota и время.

**Решение.** В `tracker.py` — реестр «идёт обновление игрока `account_id`» (lock + future по аккаунту):
второй вызов не идёт в сеть, а ждёт первый (с бюджетом) или сразу берёт БД.
**Тесты:** два потока обновляют одного игрока → клиент вызван один раз, оба получили результат.

### B3. Кэш сводок игрока по «версии данных»

**Проблема.** `build_player_summary` для каждого игрока на каждую команду грузит **всю** ранкед-историю
(`storage.get_matches`, `tracker.py:614`) и пересчитывает статистику; у ветеранов это тысячи строк.

**Решение (после замеров B0).**
- «Версия данных» игрока: счётчик `players.data_ver`, увеличивается в `add_matches`,
  `update_match_details`, `update_match_stratz`, `set_player_rank`, `set_player_anchor`.
- Кэш `PlayerSummary` по `(player_id, data_ver, локальная дата, tz, mmr_step)` в памяти (LRU).
- То же для `build_records`, `build_period_leaderboard`, `build_mmr_series` по
  `(chat_id, period, max(data_ver) игроков)` — сейчас у графика есть только TTL-кэш (`_graph_cache`).
**Тесты:** повторный вызов без изменений не читает БД (spy на storage); после `add_matches` — пересчёт.

### B4. Прогрев после новых игр

**Решение.** Когда `game_watch` нашёл новые матчи, он фоном пересобирает рейтинг чата и картинку
последнего матча (кэши B3/B5/C0). Пользователь, открывший `/stats` после оповещения, получает готовое.
Картинку для оповещения (C1) рисуем тут же и переиспользуем для «🎮 Весь матч».

### B5. Кэш полного матча Stratz

**Проблема.** `stratz.get_match` вызывается заново на `/match`, на «📝 Текстом» и будет вызываться для
«Весь матч» под оповещением.

**Решение.** LRU в `Stratz` (≈ 64 матча, TTL 10 мин для свежих матчей, 24 ч — для матчей старше суток;
`None` не кэшировать). По образцу `OpenDota._match_cache`.
**Тесты:** два вызова — один HTTP-запрос; истёк TTL — снова запрос.

### B6. «⏳ Считаю…» только когда реально долго

**Проблема.** На каждую команду бот шлёт статус и потом удаляет его (`_progress`, `_delete` в `bot.py`) —
это два лишних запроса к Telegram (~0.2–0.4 с) даже для мгновенного ответа.

**Решение.** Отложенный статус: если ответ не готов за 0.7 с — показываем `sendChatAction`
(`typing` / `upload_photo`) и только после 2 с — сообщение «⏳ Считаю…». С B1 большинство команд
уложится раньше и статус не появится вовсе.
**Тесты:** быстрый ответ → статус не отправлялся; медленный → отправлен и удалён.

### B7. Переиспользование отправленных картинок (file_id)

**Решение.** После `answer_photo` запоминать `file_id` по ключу кэша картинки. Переключение вкладок
периодов туда-обратно и повторный `/stats` без новых данных — `edit_media`/`answer_photo` по `file_id`,
без повторной загрузки PNG (это сотни КБ на каждый ответ).
**Тесты:** второй показ той же картинки отправляет строку `file_id`, а не `BufferedInputFile`.

### B8. Рендер картинок

- Шрифты и иконки самых частых героев грузить при старте (как `charts.warmup`).
- `PNG optimize=True` дорогой — замерить, при необходимости `compress_level=6` без optimize.
- Иконки после ресайза кэшировать уже уменьшенными (сейчас `resize(LANCZOS)` на каждый рендер).

### B9. SQLite (после замеров)

- Соединение открывается на каждый вызов (`storage._conn`). Проверить цену; при необходимости —
  соединение на поток (`threading.local`).
- Проверить `EXPLAIN QUERY PLAN` горячих запросов на большой БД: `get_unnotified_matches`,
  `announced_match_ids`, `get_match_ids_without_stratz`, `get_latest_match` — добавить индексы, если идут
  полным сканом (сейчас есть только `idx_matches_player_time`).
- `PRAGMA cache_size`, `mmap_size` — только если замеры покажут упор в диск.

## Часть C. Картинки вместо текста

### Принципы

1. **Картинка + короткая подпись (1–2 строки) + кнопки.** Подробности — по «📝 Текстом».
2. **Фоллбек всегда:** не собралась картинка или Telegram не принял — отправляем текущий текст.
3. **Рендер — чистая функция** `render_X_image(данные) -> bytes`, без сети и БД; иконки/аватары — готовыми
   байтами из загрузчиков с дисковым кэшем.
4. **Единый стиль:** тёмная палитра `charts.py`, ширина 1280 px, шрифт ≥ 20 px, победа зелёная,
   поражение красная, свои игроки — золото, эмодзи только в подписи (в DejaVu нет цветных эмодзи).
5. **Рендер в потоке**, кэш PNG и `file_id` (B7), пометка «данные устарели» (A3) — в подписи.

### C0. Фундамент

- `mmrbot/cards.py` — общее из `match_image.py`: шрифты, `_clean`/`_fit`, панели, «таблетки», иконка со
  скруглением и заглушкой, цветная K/D/A, точки формы, полоска винрейта, спарклайн.
- `ImageBoard(text, png, caption, markup, cache_key)` + `_reply_image(message, board)` в `bot.py`:
  фото / фоллбек / правка на месте через `edit_media`.
- Универсальная кнопка `tx:<вид>:<аргументы>` (≤ 64 байт) → текстовый рендер того же отчёта, кнопка под
  фото после нажатия убирается. `mt:` перевести на `tx:match:…` с совместимостью.
- Аватары Steam (`avatarfull` из профиля OpenDota) — загрузчик по образцу `HeroIcons`, папка `avatars/`
  рядом с БД (+ `.gitignore`). Нет аватара — кружок с инициалом.

### Тесты для каждой карточки

- Рендер: валидный PNG, ширина 1280, высота растёт с числом строк; не падает на `None`, длинных никах,
  эмодзи в нике, битых/отсутствующих иконках, пустых данных.
- Хендлеры (e2e на фейках): уходит фото с подписью и кнопками; «Текстом» даёт прежний текст и убирает
  кнопку; сбой рендера / отправки фото → текст.
- Планировщик: фото + фоллбек.
- Попиксельные «золотые» картинки не делаем (хрупко между версиями Pillow) — `render_samples.py` + глаза.

## Критерии «готово» по фазам

- **Фаза 1:** при выключенной сети (`OPENDOTA` недоступен) каждая команда отвечает ≤ 1.5 с данными из БД
  с пометкой «OpenDota недоступен с …»; в логе одна строка о падении и одна о восстановлении;
  `test_outage.py` зелёный.
- **Фаза 2:** по логам `perf` p95 текстовых команд ≤ 1 с при живом OpenDota; лишних «⏳ Считаю…» нет.
- **Фазы 3–4:** все отчёты из списка C1–C7 приходят картинкой с кнопкой «📝 Текстом»; фоллбек проверен
  тестами; картинки проверены глазами на телефоне (тёмная и светлая тема Telegram).
- **Фаза 5:** статус `/status` показывает здоровье провайдеров; сводки не теряются при сбое Telegram.
